# My VPN — Android, macOS и импорт в v2rayTun

Прямое подключение к своему VPS, без посредника. В рабочем проекте оставлены четыре режима:

| Режим | Транспорт | Назначение |
|---|---|---|
| VLESS + REALITY + Vision | TCP 443 | Основной вариант, в том числе когда UDP недоступен |
| Hysteria 2 | UDP 443 | Проверка скорости и устойчивости при потерях |
| Hysteria 2 + Salamander | отдельный UDP-порт | Другой вид пакетов, когда фильтруется обычный QUIC |
| AmneziaWG | отдельный UDP-порт | Отдельный туннель с обфускацией |

Это два режима **Hysteria 2**, не Hysteria 1 и 2. «Direct VLESS» здесь означает прямой
VLESS + REALITY/TCP к своему серверу. Обычный WireGuard, VLESS XHTTP и посредник убраны.
Ни один режим не имеет гарантии обхода любых блокировок.

## Структура

- `server/install.sh` — установка на Ubuntu 22.04/24.04.
- `server/vpnctl` — управление клиентами, миграция, экспорт.
- `server/export.py` — автономный генератор файлов для сторонних клиентов; Python 3.9+, без зависимостей.
- `config/example.json` — демонстрационный профиль с фиктивными ключами; не подключается.
- `config/android.json`, `config/mac.json` — приватные профили, исключены из Git.
- `exports/` — приватные результаты экспорта, исключены из Git.
- `android/` — собственное приложение Android, Kotlin + Compose.
- `macos/` — собственное приложение macOS, SwiftUI.
- `dist/` — готовые APK и архив macOS-приложения; вне Git.
- `tools/publish_updates.py` — шифрование и публикация новой ревизии профилей.
- `updates/` — зашифрованные профили для установленного приложения.
- `tests/` — проверки экспорта, миграции и защиты обновлений в изолированном окружении.

Собственные приложения восстановлены и обновлены до версии 1.1.0: те же четыре режима,
без обычного WireGuard, XHTTP и посредника. Предыдущие исходники и сборки остаются в
`.legacy/2026-10-15/`. Экспорт для v2rayTun сохранён как альтернативный способ подключения.

## Готовые приложения

- `dist/MyVPN-1.1.0-android-arm64.apk` — для современных Android-телефонов, Android 7+.
- `dist/MyVPN-1.1.0-android-universal.apk` — универсальная сборка для нескольких архитектур.
- `dist/MyVPN-1.1.0-macos-arm64.zip` — My VPN.app для Apple Silicon, macOS 13+.

В сборки включены отдельные текущие профили `config/android.json` и `config/mac.json`.
Сборки предназначены для личного использования: их передача другому человеку передаёт ему
и ключи VPN. Не используйте один профиль AmneziaWG одновременно на нескольких устройствах.

Android: установите APK, разрешите установку из выбранного источника и при первом подключении
подтвердите системный запрос VPN. Сохранена подпись предыдущей локальной сборки, чтобы установка
поверх неё была возможна; это локальная debug-подпись, не публикация в Google Play.

macOS: распакуйте ZIP, перенесите `My VPN.app` в «Программы» и запустите. Приложение подписано
локальной ad-hoc подписью и не нотарифицировано Apple. При первом запуске при необходимости
используйте «Открыть» в контекстном меню. Кнопка установки сетевого компонента запросит пароль
администратора; сам процесс сборки компонент не устанавливает и маршруты не меняет.
Перед подключением выключите другой VPN.

Повторная сборка:

```bash
cd android
JAVA_HOME=/opt/homebrew/opt/openjdk@17 ./gradlew assembleRelease
```

```bash
cd macos
./build.sh
```

Исходные результаты: `android/app/build/outputs/apk/release/` и `macos/build/My VPN.app`.
Для Android нужны JDK 17 и Android SDK; для macOS — Swift/Xcode Command Line Tools, Go,
Git и curl. Ядра загружаются при первой сборке. Без личных профилей используется
нерабочий демонстрационный профиль `config/example.json`.

## Обновление конфигурации одной кнопкой

На главном экране собственных приложений есть кнопка **«Обновить конфигурацию»**. Она получает
профиль из GitHub, проверяет его и сохраняет для следующего подключения. Работающий VPN
продолжает использовать снимок прежних настроек: обновление не останавливает и не переключает
туннель. При ошибке загрузки/проверки прежний профиль остаётся доступен.

Канал обновлений отделён от адреса VPN-сервера:

- `updates/android.json` и `updates/mac.json` — зашифрованные публикации в GitHub.
- `config/android-update.json` и `config/mac-update.json` — персональные bootstrap-файлы:
  URL, идентификатор клиента и ключ AES-256-GCM. Они вшиваются только в личные сборки, исключены из Git.
- Каждая публикация имеет возрастающий номер ревизии. Приложение проверяет аутентичность
  AES-GCM, соответствие устройства и ревизии, структуру профиля и отклоняет откат к старой ревизии.
- GitHub получает только ciphertext. Ключи VPN, ключи обновления и персональные APK/app
  в публичный репозиторий не отправляются. Публичные исходники собираются без вашего bootstrap;
  кнопка обновления тогда недоступна до настройки собственного канала.

Адрес сервера, ключи, порты и параметры уже поддерживаемых режимов обновляются без переустановки.
Через необязательный `profile.extraXray` можно добавить до восьми дополнительных конфигураций
протоколов, уже реализованных во встроенном Xray: VLESS, Hysteria, Trojan, VMess, Shadowsocks.
Дополнительные режимы появляются в списке после обновления; исходная публикация содержит только
четыре выбранных режима. Сначала необходимо настроить соответствующий режим на сервере.

Новый протокол, которого нет в самом ядре, требует новой версии приложения. Обновлятор получает
только данные: исполняемые файлы и скрипты не загружает. GitHub должен быть доступен из текущей
сети; при его блокировке можно загрузить настройки через уже работающий VPN или другую сеть.

Публикация после изменения сервера выполняется владельцем проекта. Сохраните новые результаты
`vpnctl profile android` и `vpnctl profile mac` в соответствующих локальных `config/*.json`.
Ключи bootstrap при этом сохраняйте прежними — установленные приложения доверяют именно им.
Затем зашифруйте новые профили и отправьте только `updates/` в GitHub.

Один раз подготовьте окружение инструмента публикации:

```bash
python3 -m venv .venv
.venv/bin/pip install -r tools/requirements-update.txt
```

Для уже настроенного проекта после замены локальных профилей:

```bash
.venv/bin/python tools/publish_updates.py --profile config/android.json --bootstrap config/android-update.json --output updates/android.json
.venv/bin/python tools/publish_updates.py --profile config/mac.json --bootstrap config/mac-update.json --output updates/mac.json
git add updates/android.json updates/mac.json
git commit -m "Update encrypted VPN profiles"
git push origin main
```

Инструмент проверяет старую публикацию прежним ключом и увеличивает ревизию. При повреждении
старого файла публикация прерывается. После отправки нажмите «Обновить конфигурацию» на нужном
устройстве. Текущий сеанс останется подключённым; новые адреса применятся при переподключении.

Для первой настройки **своего** репозитория добавьте к каждой команде `--init-url` с постоянным
HTTPS-адресом соответствующего файла, например
`https://raw.githubusercontent.com/OWNER/REPO/main/updates/android.json`. Bootstrap создаётся
только при его отсутствии. Затем соберите приложения с созданными bootstrap-файлами.
Сохраните их приватную резервную копию: потеря ключа потребует настройки нового канала
и новой сборки. Публичный зашифрованный файл не позволяет восстановить ключ.

Формат дополнительного режима в `extraXray`: `id`, `title`, `outbound`. ID начинается с
`custom-`, затем 1–48 латинских букв, цифр, `_` или `-`; название — до 80 символов.
В `outbound` разрешены только `protocol`, `settings`, `streamSettings`, `mux` по схеме
встроенного Xray. Пути к файлам, команды, изменения маршрутизации и отключение проверки
TLS отклоняются. Перед публикацией проверяйте конфигурацию с той же версией ядра.

## Импорт на Android

Установите актуальный v2rayTun из источника разработчика. В
[Android-релизе 5.24.76](https://github.com/LXST-CODE/v2RayTun/releases/tag/android-v5.24.76)
заявлены AmneziaWG 2.0, импорт/экспорт его конфигураций, Hysteria 2 через Xray и
`pinnedPeerCertSha256`. Это документированная поддержка, а не проверка каждой сборки приложения.

Сгенерировать файлы из уже сохранённого профиля:

```bash
python3 server/export.py --profile config/android.json --output exports/android
```

1. Импортируйте содержимое `exports/android/v2raytun-android.txt` из буфера обмена в v2rayTun.
   В файле три ссылки: VLESS TCP, Hysteria 2 и Hysteria 2 + Salamander.
2. AmneziaWG импортируйте отдельно из `exports/android/amneziawg.conf`. Сохраните параметры
   S1–S4, H1–H4 и I1. Если конкретная сборка не принимает файл, используйте клиент AmneziaWG;
   не преобразовывайте его в обычный WireGuard с потерей параметров.
3. Для Hysteria проверьте, что клиент сохранил `pinnedPeerCertSha256`. Это проверка конкретного
   сертификата VPS. Не включайте игнорирование проверки сертификатов как способ исправить импорт.
4. Подключайте по одному режиму. Проверьте внешний IPv4, отсутствие прямого IPv6 и DNS-утечек.
   В конфиге AWG захватывается также `::/0`; IPv6-выход на сервере не настроен. Поведение
   маршрутов/блокировки IPv6 необходимо проверить именно в используемом клиенте.

Устройства должны иметь разные ключи AWG: для телефона используйте `android`, для Mac — `mac`.

### Что означает «расширение»

Публичного SDK для добавления своего сетевого протокола внутрь v2rayTun не найдено. Реализована
интеграция через профили, тело подписки и [официальные deep links](https://docs.v2raytun.com/deep-link),
которой можно пользоваться независимо от собственных приложений:

- `deep-links.txt` — три ссылки `v2raytun://import/{configuration}`, по одной на режим Xray.
- `subscription-base64.txt` — готовое тело подписки из тех же трёх ссылок.
- `amneziawg.conf` — самостоятельный импорт AWG; неподтверждённая схема AWG URI не генерируется.
- `hysteria-native.txt` — отдельные ссылки для официального клиента Hysteria.
- `vless-xray.json`, `hy2-xray.json`, `hy2-obfs-xray.json` — диагностические конфиги Xray с SOCKS
  на `127.0.0.1:10808`; они не включают системный VPN и запускаются по одному.

Публичный сервис подписки не развёрнут. Файлы содержат ключи доступа; Base64 не является
шифрованием. Не размещайте их в публичном репозитории или открытом веб-каталоге.

Xray/v2rayTun используют `pinnedPeerCertSha256`, native Hysteria — `insecure=1` вместе с
обязательным `pinSHA256` для самоподписанного сертификата. Эти два варианта экспортируются
раздельно. Основания: [Xray TLS](https://xtls.github.io/en/config/transports/tls.html) и
[проверка сертификата в Hysteria](https://v2.hysteria.network/docs/getting-started/Client/).

## macOS

```bash
python3 server/export.py --profile config/mac.json --output exports/mac
```

Импортируйте `exports/mac/v2raytun-macos-vless.txt` в v2rayTun. На этом компьютере установлена

Для AWG есть отдельный `amneziawg.conf`; Hysteria можно использовать в клиенте с соответствующей

v2rayTun на устройствах остаётся обязательной.

## Установка и управление сервером

Для новой Ubuntu-машины сначала создайте каталог и скопируйте все три файла:

```bash
ssh root@SERVER 'mkdir -p /root/myvpn'
scp server/install.sh server/vpnctl server/export.py root@SERVER:/root/myvpn/
ssh root@SERVER 'bash /root/myvpn/install.sh'
```

Установщик сохраняет существующие ключи и создаёт `android`/`mac` только на новой установке.
Закреплены версии Xray и компонентов AWG; изменение этих версий — отдельное обновление.

```bash
vpnctl list
vpnctl add phone2
vpnctl profile phone2                 # приватный JSON
vpnctl export phone2 /root/phone2     # приватные файлы импорта
vpnctl links phone2                   # VLESS, native Hysteria и текст AWG-конфига
vpnctl remove phone2
vpnctl status
```

Для существующего сервера, где зависимости уже установлены:

```bash
install -m 755 server/vpnctl /usr/local/bin/vpnctl
install -d -m 755 /usr/local/lib/myvpn
install -m 755 server/export.py /usr/local/lib/myvpn/export.py
vpnctl migrate
```

`migrate` сохраняет `server.env`, клиентов и прежние конфиги в `/etc/myvpn/backups/`.
Он проверяет новый Xray-конфиг, исключает XHTTP, удаляет старые WG-поля, останавливает и удаляет
`wg0` только при точном совпадении с прежним конфигом этого проекта. Чужой или изменённый
`wg0` остаётся на месте с уведомлением. Повторный запуск не меняет ключи.
Файл `manifest.txt` в резервной копии описывает пути восстановления. При ручном откате сначала
верните старые файлы и версию `vpnctl`, затем восстановите прежнее состояние сервисов.
Общие правила firewall автоматически не очищаются: открытое правило без слушающего сервиса
не включает удалённый VPN. На сервере с UFW разрешаются только порты оставленных режимов.

## Amnezia через TCP

AmneziaVPN — приложение с несколькими протоколами. **AmneziaWG как протокол использует UDP**;
переключателя на TCP у него нет. См. [FAQ разработчиков](https://docs.amnezia.org/faq/).

Можно написать внешнюю обёртку, которая передаёт UDP-датаграммы через TCP/TLS, но она нужна
на обеих сторонах. На Android её пришлось бы встроить в собственный VPN-клиент: два независимых
VpnService нельзя считать универсальной схемой каскада. Надёжная доставка TCP добавляет задержки
при потерях, а распознавание самой обёртки остаётся возможным. Для текущего проекта резерв при
недоступном UDP — VLESS + REALITY/TCP, без усложнения AWG.

## Что действительно влияет на обход блокировок

Ниже инженерные выводы из архитектуры, а не результаты испытаний у всех российских операторов.

| Причина отказа | Что может помочь | Что само по себе не решает проблему |
|---|---|---|
| Фильтрация узнаваемого протокола | Смена транспорта/обфускации | Только новый номер порта |
| Недоступен UDP | Рабочий TCP-транспорт | Salamander и AWG тоже остаются UDP |
| Блокировка IP VPS | Другая доступная точка входа | Смена протокола на том же адресе |
| Строгий список разрешённых адресов | Реально разрешённый узел, умеющий передать данные дальше | Чужой домен в SNI |
| Плохой маршрут/потери | Другой маршрут, сравнение TCP и QUIC | Автоматическое добавление посредника |

### VK, CDN и посредник

`SNI=vk.com` не направляет соединение через VK: IP назначения остаётся вашим VPS.
[REALITY target/serverNames](https://github.com/XTLS/Xray-docs-next/blob/main/docs/en/config/transports/reality.md)
управляют поведением TLS; это не разрешение использовать чужую инфраструктуру как прокси.
Для реального транзита нужен контролируемый узел или API, который позволяет обеим сторонам
обмениваться данными. VPS в VK Cloud не становится автоматически разрешённым адресом `vk.com`.

Domain fronting работает только при соответствующем поведении конкретного сервиса; например,
[Cloudflare документирует отказы при некоторых несовпадениях SNI/Host](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/4xx-client-error/error-421/).
Прямой REALITY/TCP нельзя направить через обычный HTTP CDN простой заменой IP.

Посредник может улучшить связь, если прямой маршрут ограничен, а оба участка через него хороши.
Он также добавляет задержку, расход трафика и ещё одну точку отказа. При хорошем прямом маршруте
ускорение не ожидается. Пока посредник не используется и его команды убраны.

### Есть ли смысл в собственном необычном протоколе

Новый формат пакетов без проверки может стать новой сигнатурой. Практически интересны три
направления; ни одно не устраняет блокировку своей точки входа:

1. **Обычный HTTPS с восстановлением сессии.** Проверенный HTTP/2-стек, TLS 1.3, свой домен
   и действительный сертификат. Основной режим — потоки POST/GET; если длинные соединения
   обрываются, переход на короткие запросы с номерами блоков, подтверждениями и дедупликацией.
   Польза возможна только если короткие запросы проходят там, где потоки действительно режутся.
   Упаковка добавляет задержку, а размеры/частота запросов по-прежнему видимы. Часть этой идеи уже
   покрывают [XHTTP](https://github.com/XTLS/Xray-core/discussions/4113) и
   [WebTunnel](https://community.torproject.org/relay/setup/webtunnel/), поэтому нужен контрольный
   эксперимент, а не заявление о новом нераспознаваемом протоколе. XHTTP в текущем сервере отключён.
2. **WebRTC с собственным TURN.** Реальный DataChannel и проверенные библиотеки, свой signaling.
   Это даёт другой путь соединения, но STUN/DTLS/TURN тоже распознаются, а TURN/TLS на порту 443
   не становится HTTPS. [RFC 8831](https://www.rfc-editor.org/rfc/rfc8831.html) и
   [RFC 8656](https://www.rfc-editor.org/rfc/rfc8656.html) описывают эти механизмы.
   Пример существующей архитектуры — [Snowflake](https://snowflake.torproject.org/), где существенную
   роль играет множество посредников. Один TURN на том же заблокированном IP не даст такого свойства.
3. **Зашифрованные объекты в собственном облаке.** Клиент и сервер читают/пишут блоки через
   штатный HTTPS API. Это может быть запасным каналом доставки нового адреса или профиля,
   если облако доступно. Для видео и интерактивного VPN мешают опрос, задержка, квоты и цена операций.
   Существование API не означает его доступность при конкретном белом списке.

Новые алгоритмы шифрования для этого не нужны. Если посредник завершает TLS, требуется также
проверенная сквозная защита, доверенные ключи и защита от повторов. На Android обычный стек
[Chromium/Cronet](https://developer.android.com/develop/connectivity/cronet) может быть основой
HTTPS-эксперимента, но сходство библиотеки с браузером не скрывает поведение приложения.

Сейчас нет воспроизводимых данных, что такой прототип даст преимущество перед четырьмя
оставленными режимами. Поэтому экспериментальный транспорт не внедрён. Собственные приложения
собраны по отдельному запросу и используют существующие Xray и AmneziaWG. Сначала полезно измерить успешность подключения, время соединения, p50/p95 задержки,
скорость и устойчивость 15-минутной сессии на Wi-Fi и мобильной сети. Затем — проверять конкретную
гипотезу на доступном собственном домене и сравнивать при одинаковом маршруте. Если преимущество
подтвердится, новый транспорт можно добавить в собственные приложения.

## Проверка и диагностика

```bash
.venv/bin/python -m unittest discover -s tests -v
bash -n server/install.sh server/vpnctl
```

Проверки Android без установки на телефон:

```bash
cd android
JAVA_HOME=/opt/homebrew/opt/openjdk@17 ./gradlew testReleaseUnitTest lintRelease
```

Проверки macOS без запуска VPN и установки сетевого компонента:

```bash
python3 macos/scripts/check-configs.py
```

Проверяются расшифровка, повреждение данных, чужой ключ/клиент, откат ревизии и дополнительные
режимы. macOS-проверка использует отдельное хранилище настроек и `xray run -test`.
Приложения не запускались для переключения туннеля: проверка реального подключения с
устройств остаётся отдельным шагом, чтобы не прерывать используемый сейчас VPN.

Тесты сервера используют `MYVPN_ROOT` и заглушки сервисных команд; боевые сервисы не затрагиваются.
Это проверки жизненного цикла клиентов, миграции/резервных копий, удаления только проектного WG,
набора протоколов, кодирования ссылок, защиты pin, прав файлов и недопустимых входных данных.
Проверка синтаксиса конфигурации ядром не заменяет передачу данных через сервер.

15 октября 2026 года миграция применена к существующему VPS. Ключи и настройки оставленных
режимов совпали с прежними профилями. После обновления прямые подключения Xray через физический
интерфейс Mac успешно прошли для VLESS, Hysteria 2 и Salamander; внешний IP совпал с IP VPS.
Неверный сертификатный pin был отклонён. AmneziaWG активен, экспорт проходит `awg-quick strip`;
рукопожатие с Android и импорт в интерфейс v2rayTun здесь не проверялись. Все 17 тестов прошли.

При диагностике обнаружено, что включённый на Mac v2rayTun перехватывает обычный маршрут
тестового Xray: это вызывало сбои REALITY/Hysteria через порт 443. Привязка только тестовых
сокетов к физическому интерфейсу устранила влияние вложенного VPN. Системные настройки
подключённого v2rayTun не менялись.

При проблемах на сервере:

```bash
vpnctl status
journalctl -u xray -n 50 --no-pager
awg show awg0
```

Факт запуска сервиса не означает успешное соединение клиента. Проверяйте внешний адрес и
последнее рукопожатие AWG. Проверки из одной сети нельзя обобщать на другие операторы и регионы.

Данные доступа со скриншота не включены в код. Сам скриншот, профили, экспорты и локальный архив
исключены из Git. Опубликованный root-пароль стоит сменить; SSH-ключ уже позволяет войти без него.
